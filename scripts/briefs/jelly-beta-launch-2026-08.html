A0 · Security — fix before any invite goes out

Every item below was independently re-confirmed by an adversarial verifier agent against live code. These are ordered by how much damage a stranger with a browser can do.
1 · Account takeover on the admin email. app/api/auth/register/route.ts:62-77 attaches a new password to any existing User that has no credentials. The owner's admin address sits on both the admin and vater-owner allowlists, has zero credentials, and MFA is unenforced — so a single unauthenticated POST claims it. This is the finding that makes "just send a few invites" impossible today.
2 · Cross-tenant job leak. GET /api/vater/pipeline-status returns every user's jobIds, projectIds, and lastLog to any signed-in account. GET /api/vater/autopilot/jobs/[jobId] then proxies the whole job — script, prompts, costs, finalVideoUrl. Any invitee could read every other customer's work in two requests.
3 · Voice library wide open. DELETE /api/vater/voices/[id] and GET /voices/[id]/sample need only a session — any signup can delete or download your and Monroe's voice clones. GET /api/vater/voices lists all 22 clones, including Jared-A through Jared-D.
4 · Free unmetered renders, and a self-inflicted outage. POST /api/vater/topic has no checkBudget, and all 17 system styles default to firered-local + f5-tts. So a public user's render runs on the GB10, calls vater_runway.clear() — which stops 17 production services — and auto-starts comfyui-vater, violating the standing VATER = MODAL-ONLY rule.
5 · Studio tier sees and edits everything. lib/vater/project-access.ts:33 returns an empty filter for studio emails; GET /api/vater/direct lists all Direct jobs; and summary.ts:118 sums all projects into Trey's bill — so a second studio user would both see his work and distort his invoice.
6 · Model A Stripe path is armed and untested. Live key, pricing.ts per-action prices, zero charges ever made and zero subscription rows — meaning the first real card triggers an untested billing path at ~$25/video against a UI promising ~$3.
7 · The basics are missing. No login rate-limit. No password reset. JWTs valid 30 days with no revocation. One shared ElevenLabs key — any user can drain your plan.
What this costs to fix: one day. Phase 1 on page 10 is nine concrete edits, all inside ~/tolley-site except the render-semaphore change in vater.py. Nothing here needs new infrastructure and nothing here needs a decision from you.
The reassuring half: isolation between users is data-only by design — there are no per-user Modal apps, containers, or notebooks to get wrong. The leaks above are all missing WHERE userId = … clauses and missing auth guards, not an architecture that has to be rebuilt.

A1 · Billing truth  ·  A2 · Unit economics

What the system currently charges, what a minute of video actually costs, and where the money leaks.

A1 — Three prices coexist today

  • The landing says "~$25/video"; lib/vater/pricing.ts holds per-action Stripe pricing (armed, 0 charges ever, 0 VaterSubscription rows); ops-fee.ts/summary.ts compute cost + $0.35/min (report-only, Zelle). Three answers to "what does this cost" is two too many.
  • No prepaid credit or balance concept exists for Vater — but a proven prepaid-pack pattern does exist for /video/studio (lib/stripe-webhook.ts:496-527 fulfillVideoCredits, STRIPE_PRICE_VIDEO_PACK_*). Clone it.
  • Stripe Billing Credits require metered subscriptions and add 0.7% per applied credit — do not use them. Own the Prisma ledger and use Checkout in mode:'payment'. (stripe.com/pricing)
  • ops-fee.ts:18 reads a DGX path that does not exist on Vercel, so the production rate is effectively a hardcoded 0.35 — move it to VATER_OPS_RATE_PER_MIN.
  • Per-video receipt data (compute, ops, minutes) already exists on the cards and lightbox; render wall-time is shown nowhere.

A5 · Onboarding, auth & isolation  ·  A6 · Capacity

What a tenth user would actually experience today, and what breaks first when they all render at once.

A5 — The onboarding reality

  • Signup is fully open (/signup?callbackUrl=/animate): no invite code, no email verification, no password reset. Tiers are Vercel environment-variable allowlists — every new user is an edit plus a redeploy.
  • The public golden path has never been run end-to-end by anyone. The audit harness fakes all POSTs, and Trey is the only account with projects. Nobody has actually walked signup → style → project → render → download.
  • Good news on infrastructure: a new user needs no Modal app, container, or notebook. Modal apps are shared, containers are per-call, the DGX runs one shared orchestrator. Isolation is data-only (userId) — which is exactly why the A0 leaks matter so much.
  • Voices and characters are flat shared directories on the DGX keyed by name (vater_voices/, ~/vater-studio/characters) — user #2 collides with user #1. Namespacing is a Phase 3 item.
  • No impersonation or view-as exists. No feedback capture beyond a mailto link. No version or changelog. No error tracker — log.ts is a production no-op.
  • Publishing: per-user YouTube OAuth exists but the start route is studio-gated (403 for public users). Every other platform is a stub.

The concurrency ceiling right now: vater.py spawns an unbounded thread per render with no semaphore, while Modal Starter allows 10 concurrent GPUs workspace-wide — shared with the Lady and shorts lanes. That works out to 3–4 simultaneous Vater renders today. The DGX side of the job is CPU (ffmpeg, whisper) and RAM: 27 GB free with swap at 86%.
Two observability gaps that will bite during a beta: per-user logs are not durable (a 30-line ring buffer and a 40-job prune), so a user's failure is gone before you can look at it. And the LLM cost meter is process-wide, so it mis-attributes spend across concurrent users — which quietly corrupts per-video receipts the moment two people render at once. Phase 1 makes the meter per-job; Phase 3 adds the durable VaterEvent log.
Onboarding is genuinely turnkey once styles default to Modal. There are zero DGX steps and zero Modal steps for a new user — the entire "how do I set this person up" answer becomes: mint an invite code, they sign up, they add a card, they get $10.

A8 · Legal  ·  A9 · Domain & brand

The paperwork gap is real but small — and the pattern for closing it already exists in this codebase.
Today there is no legal coverage for /animate at all. /terms and /privacy are T-Agent / SMS pages dated February 2024 that never mention the product. Nothing records ToS acceptance for /animate users — there is no termsAcceptedAt, and Trey has no acceptance on file either.
The fix is a known pattern. The estate lane already proved per-brand legal pages: lib/legal-estate.ts plus app/estate/terms|privacy. Phase 3 clones it as lib/legal-animate.ts + app/animate/terms|privacy|beta through the shared components/legal/legal-page-shell.tsx.

Clauses the beta must have

  • User owns their outputs — stated plainly, first.
  • Showcase + improvement licence with an opt-out — modelled on Suno's "operating, improving, promoting" and Midjourney's survives-termination wording (decision #4).
  • Beta AS-IS, no SLA — on its own /animate/beta addendum page.
  • Voice-clone consent attestation — Tennessee ELVIS Act, California §3344, New York §§50–51.
  • Credit expiry: prepaid credits non-refundable; purchased credits do not expire (or 12 months); promo credits 30–60 days.
  • YouTube API Services block — Google policy III.A, reproduced verbatim; required by their terms.
  • Subprocessor list — Modal, Kimi / Moonshot (China), fal, Gemini, ElevenLabs. The China disclosure is not optional.
  • Blob finals are public-unlisted URLs — disclose it; users assume otherwise.
  • TAKE IT DOWN Act — a 48-hour removal path.

Why a Prisma ledger rather than Stripe Billing Credits: Stripe's credit product requires metered subscriptions — which decision #3 rules out — and charges an extra 0.7% on every applied credit. Owning the ledger costs one table and gives you refunds, promo expiry, and reconciliation adjustments that Stripe's version does not model.
The good news on effort: almost nothing here is novel. The pack→webhook→fulfil path already runs in production for /video/studio, the cost math already runs in ops-fee.ts, and the per-video receipt data is already computed and displayed. Phase 2 is mostly wiring three existing systems to each other and adding the ledger they write to.
Do not skip the idempotency key. Stripe retries webhooks. A fulfillVideoCredits clone without event-id deduplication will credit a pack twice on any retry — and unlike a double charge, a double credit is invisible until the margin is already gone.
